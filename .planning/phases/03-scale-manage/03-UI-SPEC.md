## Spacing Scale

Inherited from Phase 1 UI-SPEC. No changes. Quasar utility class equivalents shown for executor reference.

| Token | Value | Quasar class | Usage |
|-------|-------|--------------|-------|
| xs | 4px | `q-pa-xs` / `q-ma-xs` | Icon gaps, badge padding, inline chip spacing, filter chip gaps |
| sm | 8px | `q-pa-sm` / `q-gutter-sm` | Compact element spacing, button row gaps, filter bar internal gaps |
| md | 16px | `q-pa-md` / `q-gutter-md` | Default element spacing, form field gaps, table cell padding, dialog section gaps |
| lg | 24px | `q-pa-lg` / `q-col-gutter-md` | Card padding, section padding, dialog padding, filter bar section spacing |
| xl | 32px | `q-pa-xl` | Dialog padding (`q-pa-lg q-pt-xl` — events pattern) |
| 2xl | 48px | — | Major section breaks |
| 3xl | 64px | — | Reserved; not used in Phase 3 |

Exceptions (Phase 3 additions):
- **Filter bar height:** The filter controls row sits at approximately 48px tall (compact `q-input`/`q-select` with `dense` + `filled`). Not on the 8-point scale by design — it matches Quasar's default dense input height.
- **Multi-select checkbox column:** 48px wide column in the q-table for the checkbox. Matches the existing auto-width expand column pattern.
- **Touch targets (mobile):** minimum 44px height for all interactive elements. Quasar `size="lg"` on buttons satisfies this. Dense inputs in the filter bar are exempt (desktop-first admin tool).

**CSV validation table columns:**

| Column | Data | Notes |
|--------|------|-------|
| # | Row index (1-based) | Fixed width |

**CSV validation summary banner (D-07):**
- When all rows valid: `q-banner` with `color="positive"`, icon `check_circle`, text "{N} valid rows ready to create."
- When errors exist: `q-banner` with `color="warning"`, icon `warning`, text "{X} valid, {Y} errors. Fix all errors in your CSV and re-upload before creating."
- When row count exceeds 500: `q-banner` with `color="negative"`, icon `error`, text "CSV has {rowCount} rows. Maximum is 500. Remove excess rows and re-upload."

**CSV template download (D-05 discretion — column naming):**
- Button: "Download Template" — `q-btn flat dense color="grey"` with `icon="download"`.
- Downloads a CSV file with headers: `recipient_name,amount_sats,recipient_email,nostr_npub,sender_name,message`.
- Includes one example row: `Alice,1000,alice@example.com,,Bob,Happy birthday!`.
- File name: `giftcards_bulk_template.csv`.
- Hint text below button (text-caption): "Required: recipient_name, amount_sats. Optional: recipient_email, nostr_npub, sender_name, message."

**CSV file selection behavior:**
1. Issuer selects file via `q-file`.
2. Frontend reads file content (or sends to server for parsing — RESEARCH.md recommends server-side parsing with `csv.DictReader`).
3. Show `q-spinner` in file input while parsing.
4. Server returns per-row validation result: `[{rowIndex, valid, recipient_name, amount_sats, recipient_email, nostr_npub, errors: []}]`.
5. Frontend renders validation table + summary banner.
6. If any errors: submit button disabled, banner shows error count.
7. Issuer fixes CSV, re-uploads → validation re-runs.
8. When all rows valid: submit button enabled, label "Create {N} Cards".

**Submit label (dynamic):** "Create {validCount} Cards" — e.g., "Create 47 Cards".

**Submit disabled condition:** No file uploaded, any validation errors, row count > 500, or wallet not selected.

#### Bulk Create Submit Behavior (shared)

1. Issuer clicks submit → form validates.
2. **Same Amount tab:** `POST /giftcards/api/v1/cards/bulk` with `{wallet, count, amount, recipient_name, sender_name, message, expires_at, design}`.
3. **CSV tab:** `POST /giftcards/api/v1/cards/bulk` with `{wallet, rows: [...validatedRows], design_mode, design}` (or re-upload file with design config).
4. Show `q-spinner` in submit button (`:loading="bulkDialog.loading"`).
5. Server creates cards in a loop calling `create_gift_card()` (RESEARCH.md — all-or-nothing or batch-with-progress at planner's discretion).
6. On success: close dialog, `notify('{N} gift cards created successfully!', 'positive')`, refresh card list + wallet balance.
7. On partial failure (if batch strategy): `notify('{X} of {N} cards created. {Y} failed: {error}', 'warning')`, refresh card list to show created cards.
8. On total failure: `notifyApiError(error)`, keep dialog open.
9. **No results table in dialog (D-03):** The dashboard IS the results view. Newly created cards appear in the filtered dashboard after refresh.

### Bulk Create — CSV upload validation

| Validation | Trigger | Behavior |
|------------|---------|----------|
| File type | File selected | Reject non-`.csv` files with `notify('Please upload a CSV file.', 'negative')` |
| Row count | After parse | If > 500 rows: show negative banner, disable submit |
| Per-row: recipient_name | After parse | Required — if empty, row marked invalid with error "recipient_name is required" |
| Per-row: amount_sats | After parse | Required, integer ≥ 1 — if invalid, row marked invalid with error "amount_sats must be a positive integer" |
| Per-row: recipient_email | After parse | Optional, but if present must be valid email format — if invalid, row marked with error "Invalid email format" |
| Per-row: nostr_npub | After parse | Optional, but if present must be valid npub format — if invalid, row marked with error "Invalid npub format" |

**Two-phase CSV flow (D-07):**
1. Upload → server parses + validates → returns per-row validation result.
2. Frontend renders validation table + summary.
3. If any errors: submit disabled, issuer must fix CSV and re-upload.
4. Only when all rows valid: submit enabled.
5. No partial create — all-or-nothing (D-07).

2. Frontend iterates over target cards, calls `POST /giftcards/api/v1/cards/{id}/deliver` per card.
3. Show progress: `q-spinner` in button + toast "Sending {X}/{N}...".
4. Skip cards without `recipient_email` — count as skipped.
5. On completion: `notify('{N} emails sent, {M} skipped (no email address)', 'positive')`.
6. Refresh card list (delivery status badges update).
7. If some fail: `notify('{N} sent, {M} failed. Check email configuration.', 'warning')`.

### CSV template download

1. Issuer clicks "Download Template".
2. Frontend generates CSV string with headers + one example row.
3. Browser downloads `giftcards_bulk_template.csv`.
4. `notify('Template downloaded', 'positive')`.

### CSV export (filtered/selected)

1. Issuer clicks "Download CSV" or "Download CSV (Filtered)".
2. Frontend builds CSV from selected or filtered cards.
3. CSV columns: `card_id, amount, status, recipient_name, sender_name, message, recipient_email, email_status, redemption_url, created_at, expires_at, redeemed_at` (D-04, specifics).
4. Browser downloads `giftcards_filtered_{date}.csv` or `giftcards_selected_{date}.csv`.
5. `notify('CSV exported successfully', 'positive')`.

## Accessibility Notes

- All `q-btn` elements that are icon-only must include `aria-label` (e.g., `aria-label="Delete gift card"`, `aria-label="Edit gift card"`, `aria-label="View full details"`).
- Bulk action buttons have visible text labels (not icon-only) — no additional aria-label needed beyond the text.
- CSV validation table status column uses icon + color (not color alone) to satisfy WCAG 1.4.1 — `check_circle` (positive) for valid, `error` (negative) for errors.
- Error rows in the validation table have a light red background tint (`bg-red-1`) AND an error icon AND error text — triple-redundant status communication.
- Delete confirmation dialog is `persistent` (requires explicit action to close) — prevents accidental dismissal of a destructive confirmation.
- Filter controls are keyboard-accessible: `q-select`, `q-input`, and `q-date` all support keyboard navigation natively via Quasar.
- Multi-select checkboxes are keyboard-accessible: Quasar's `selection="multiple"` renders native checkbox semantics with keyboard support.
- Date range popup (`q-popup-proxy`) must be dismissible via Escape key (Quasar default behavior).
- Tab navigation in bulk dialog (`q-tabs`) must be keyboard-accessible: Tab key moves between tabs, Enter/Space activates (Quasar default).
- Card image preview in detail dialog must include `alt="Branded gift card image"`.
- Status badges include both color AND label text (not color alone).
- Edit and Delete buttons disabled for redeemed cards must include tooltip text explaining why ("Redeemed cards cannot be edited/deleted").
